# Bringing an agent into the dashboard

The dashboard (`frontend-msp`) is ONE app at ONE address. Every agent is a module of it: the dashboard draws the common things (the sidebar with the agent's
navigation, **Switch agent** and the signed-in person; the top bar; sign-in; loading states) and the agent gives its **screens**. The agent's screens call
the agent's own API through the dashboard's address: `/agents/<id>/api/...` (CloudFront sends that to the agent's live API; `agents/<id>/manifest.json`).
The isolated agent (its repository, its own site) is never changed: the dashboard keeps its own copy of the screens, produced from the isolated source by
a re-runnable script.

## What you deliver

```text
src/features/<id>/
  module.tsx          hand-written: the AgentModule (below) — navigation, titles, providers, which screen for which page
  adapters/           hand-written glue (routing shims, API client base, portal container ...), small
  app/                GENERATED by agents/<id>/port.mjs from the isolated source (do not edit by hand; change the script)
  ...tests            next to the code they test
agents/<id>/port.mjs  copies the isolated source into src/features/<id>/app/ and applies scripted adaptations (each edit must match exactly once, or the script stops)
agents/<id>/NOTES.md  what was adapted and why, how to re-port, what is NOT verified
agents/<id>/manifest.json  (exists) update it if you learn the API origin/hosts are different
public/agents/<id>/   static files the agent's screens load by URL (images, sample files, fonts) — they are then served at /agents/<id>/...
```

The default export of `src/features/<id>/module.tsx` is an `AgentModule` (`src/features/agents/types.ts`): `id`, `subtitle`, `defaultPage`, `nav` (sections of
`{id, label, icon, badge?}`), `Screen` (gets `{route:{page,params}, navigate}`), `titleOf(route)`, and optionally `Provider` (the agent's own providers: a
query client, SWR config ...), `useNavBadges` (live counts in the sidebar), `SidebarExtra` (e.g. the WAFR customer menu), `activeNav`, `fullWidth`.
A stand-in module exists for every agent: replace it.

## The shell gives you (do not rebuild these)

- **Sidebar**: logo, agent name + subtitle, your `nav`, Switch agent, the person's card with Sign out, collapse. Your pages must NOT draw their own sidebar, logo,
  account card, Sign out, sign-in gate/page, or a theme switch. Keep the agent's own look otherwise.
- **Top bar**: breadcrumb `Ingram Micro Agents > <agent> > <titleOf(route)>`. Content that the isolated top bar had on the right (a Refresh button, an account picker, a status
  badge) goes in with `<TopbarActions>…</TopbarActions>` from `@/features/shell/topbar-slot`.
- **Routing**: there is no URL routing: the address never changes. A "page" is a string (`start`, `review`, `incident`) with string `params` (`{id:'R-1'}`).
  Replace the agent's router (Next App Router, react-router, a hash router, tab state) so that the page comes from `route` and moving uses `navigate(page, params)`.
  Links and buttons that went to a route call `navigate`. Provide small shims for what the agent imports (`next/link`, `next/navigation`'s `useRouter/usePathname/
  useSearchParams/useParams`, `react-router-dom`'s `Link/NavLink/useNavigate/useParams`) in `adapters/` and have the port script rewrite the imports.
  State that used to live in the address (`?tab=`, `#/runs/<id>`) becomes `params`.
- **Session**: the person is already signed in (shared Cognito pool). If the agent's API needs the token, `import { idToken } from '@/shared/auth/cognito'`.
- **Toasts**: the dashboard mounts one `<Toaster>` (sonner). If the agent's own toast helper needs its own provider, put it in the module's `Provider`.
- **Lazy**: your module is its own chunk; it is only downloaded when the agent is opened. Keep heavy libraries (reactflow, docx, pdf) behind dynamic imports where the isolated code did.

## The API

Every call goes to `agentApiBase('<id>')` + the path the agent already uses (`@/shared/api/agent-api`): `/agents/secops` + `/api/runs`. No absolute API URL, no
environment variable for it. If the agent calls another host straight from the browser (an S3 presigned upload), it stays; list the host in `manifest.json`
`externalHosts` (the Content-Security-Policy is built from it) and anything that must change outside this repo in `needsAws`.

## Styles

- Tailwind v4 is the dashboard's: utility classes work as they are (the tokens `--color-*`, `--radius-*`, `--shadow-*` are the same Ingram Micro ones the agents use).
- An agent's own global CSS (plain stylesheets, or custom classes in a `globals.css`) would reach the sidebar and the other agents. Pass it through
  `node scripts/scope-css.mjs msp-<id> <in.css> <out.css>`: every rule is put under `.msp-<id>`. Render the agent's screens inside `<div className="msp-<id>">` (in `Screen` or
  `Provider`). A dialog, menu or toast React draws into `document.body` is OUTSIDE that element: give the portal the scope class too (Radix `container`/`className`, or a
  portal root you create with the class), and check each dialog/menu/toast in the browser.
- Keep the agent's look exactly as the isolated one: same spacing, components, motion. Compare screenshots.

## Working (no one else is disturbed)

1. `scripts/clone-workspace.sh <scratch>/<id>` makes a private copy with the shared node_modules (hard-linked: NEVER run `npm install` there; if a package is missing,
   say so in your report, the lead installs it for everyone).
2. Work in the copy. Type-check/lint/test there (`npm run typecheck`, `npm run lint`, `npm test -- <path>`). Build with `scripts/locked-build.sh` ONLY (it takes a turn: builds are one at a time
   and need about 1.5 GB; it removes `.next` after). `next dev` is fine on your own port (5410 secops, 5420 wafr, 5430 sre, 5440 devops, 5450 onboarding).
3. Run it with the agent's API stubbed: `node scripts/dev-proxy.mjs --port <p+1> --app http://127.0.0.1:<p> --<id> http://127.0.0.1:<fake>` sends `/agents/<id>/api/...` to your fake
   API (strip the prefix: the fake sees `/api/...`). Earlier test harnesses with fake APIs: `agents/<id>/embedded/` and the scratchpad `secops-harness`, `wafr-harness`, `sre-harness`.
4. A signed-in session for tests: seed the Cognito library's keys in sessionStorage before the page loads (see `integrated-check.mjs` in the scratchpad `msp-harness` for the exact keys and a token that passes).
5. When finished, copy back ONLY `src/features/<id>/`, `agents/<id>/` and `public/agents/<id>/` to the real tree (commands in `clone-workspace.sh`). Do not touch anything else there.

## Done means (all verified in a real browser, desktop 1440x900 and 1024x768, no phone)

- every page/tab/state of the isolated agent exists and behaves the same; no console errors; no failed requests except those a test provokes on purpose; no horizontal overflow
- the agent's API calls all go to `/agents/<id>/api/...`; axe: no violation the isolated app does not also have
- the agent's CSS does not leak: the sidebar and top bar look the same before and after the agent is opened, and after switching to another agent and back
- unit tests for the adapters and for the screens you changed; `npm run typecheck` and `npm run lint` clean in the copy
- `port.mjs` re-run on a clean copy reproduces `src/features/<id>/app/` exactly (idempotent)
- the isolated repository is unchanged (`git status --porcelain` identical before and after)
