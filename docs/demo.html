INGRAM Landing Zone Agent — demo
From a statement of work to a running AWS landing zone

An agent reads the customer's SOW, designs the landing zone, generates and validates the infrastructure code, then builds it in the customer's AWS account through AWS Transform. A person approves anything that creates or changes AWS resources.

What the agent does

  • Reads the SOW and maps every requirement to a landing zone decision
  • Cites the SOW text behind each decision, or marks it inferred
  • Writes Terraform and CloudFormation, then validates and security-scans both
  • Answers AWS Transform's build questions from the approved design

What it never does

  • Approve anything that creates or changes AWS resources
  • Invent a value the SOW does not state — it raises an open question instead
  • Apply the AI-written policies automatically
  • Close an AWS Transform job on its own say-so

Open with the problem. A landing zone normally takes four to eight weeks: discovery workshops, architecture design, deployment, then review cycles between migration, security and the business.

This takes the SOW the customer already signed and produces a reviewed, validated design in minutes, then builds it. The figures on screen are from a real run, not a mock-up.

Set expectations now: a person still approves every change that touches AWS. That is deliberate, and it is the first question security teams ask.

Point at the rejection line in the history. The agent tried to save a design claiming a quote from the SOW, the platform could not find that quote in the document, and it refused the save.

That check is the core of the trust model. Every decision must either quote the SOW or be labelled as inferred. The agent cannot assert something the document does not say. It retried and got it right.

If asked: yes, that costs time. It took four attempts here. We would rather retry than ship a design with an invented justification.

    "Resource": "*",
    "Condition": { "ArnNotLike": {
      "aws:PrincipalArn": "arn:aws:iam::*:role/{{ADMIN_ROLE_NAME}}" } }
  }]
}

This was the gap the team raised. The generated policies previously shipped with {{PLACEHOLDER}} values that somebody had to find and hand-edit in a JSON file.

Now each placeholder is a labelled field with its description and an example. The raw JSON stays editable for anything the fields do not cover, and the server re-checks on save: Deny-only, inside the AWS size limit, and a value cannot break out of the JSON structure.

Be clear on the boundary: saving updates the downloadable code. It does not touch the customer's organization. Applying these is a separate, deliberate step.

This is the heart of the product. Transform asks a long series of questions. The agent answers the ones the approved design already settles, and refuses the rest.

Read the blue box aloud. The agent explains its reasoning and names the option it would pick, but a person presses the button. Options that start execution — Proceed, Approve, Deploy for me — are refused in code, not by asking the model nicely. Anything unrecognised goes to a second reviewer model that fails closed.

Expect "why not fully automatic?" The answer: these actions create AWS accounts and cannot be undone. Closing an AWS account takes up to 90 days.

Audit

Every tool call, every answer, and who gave it — the agent or a named person — is recorded against the run and cannot be edited from the app.

This slide answers "how do I know it worked?" Not because the model said so. The platform calls AWS Organizations and Control Tower, compares what it finds against the approved design, and only then closes the job.

The attestation names what was observed before and after, and any gap against the design. That is the artifact a customer's security team can keep.

Where the guardrails sit

The division of labour, in one view. This is the slide to leave on screen during questions.

The agent decides

Model
  • Mapping the SOW to OUs, accounts, policies and controls
  • Writing custom policy JSON, for human review
  • Answering Transform questions the design already settles
  • Choosing between paths that change nothing in AWS

Checked by

Quote verification against the SOW, a second reviewer model on every typed reply, and a per-run cap on how many answers the agent may send.

A person decides

Human
  • Approving the plan so the build starts
  • Any option that creates or changes AWS resources
  • Values the SOW does not state, such as root emails
  • Whether to apply the AI-written policies at all

Enforced by

A refusal in code, not a prompt instruction. The tool rejects these options whatever the model asks for, and hands them over with the exact wording.

What AWS owns, and we cannot change

AWS

Transform builds in two rounds: the foundation first, then the workload OUs and accounts once it has designed them from your answers.

Round 1
Landing Zone - Base, Configure AWS CloudTrail — Control Tower, the Security OU and the shared accounts
Round 2
Organizational Unit hierarchy, preventive guardrails, Accounts

Use this for the hard questions. Three parts: what the model does, what a person does, and what belongs to AWS.

The last card matters if anyone asks why the deployment happens in two passes. That split is Transform's, because it designs the workload accounts only after the foundation conversation. We cannot collapse it into one stack, though we may be able to reduce it to a single deployment round.

What this changes

Before

  • Four to eight weeks for a landing zone, longer when regulated
  • Discovery workshops to re-establish what the SOW already says
  • Design quality depends on who is available
  • The link from a requirement to a built control lives in someone's head

With the agent

  • Validated design and code in minutes from the signed SOW
  • Every decision quotes the SOW or is marked inferred
  • The same catalog of policies and controls on every engagement
  • An attestation of what was built, with a full audit trail

Honest limits

  • AWS Transform is required for the deploy path, and it owns the build sequence
  • Foundation scope only: OUs, accounts, catalog policies and controls. Not networking or workloads
  • The AI-written policies are delivered for review and are never applied automatically
  • Security scan findings are reported, not blocking. A person judges them

Close on the limits, not the benefits. Naming what the product does not do is what makes the rest credible, and it stops a customer discovering a boundary later.
